# Спека: онбординг в 2 шага

> ⚠️ Пример для наглядности — из нашей гипотезы H-000. Удали или замени под свою фичу.

| Поле | Значение |
|------|----------|
| Фича | Короткий онбординг (5 шагов → 2) |
| Связанная гипотеза | `hypotheses/H-000-EXAMPLE.md` |
| Дата | 2026-08-06 |
| Статус | Готова к `/feature` |

## 1. Гипотеза

> **Мы считаем, что** сокращение онбординга с 5 шагов до 2 (остальное — позже, по мере надобности)
> **для** новых пользователей на первом входе
> **приведёт к** росту доли завершивших онбординг,
> **потому что** пользователь быстрее видит ценность и не выгорает на форме.

- **Ведущая метрика:** доля дошедших до конца онбординга.
- **Итоговая метрика:** retention D7.
- **Критерий успеха:** завершаемость ≥ 75% (было 38%), D7 не падает.

## 2. Проблема

- **Наблюдение:** 62% новых пользователей бросают онбординг до 4-го из 5 шагов (аналитика за июль).
- **Интерпретация:** пять экранов подряд читаются как длинная анкета, ценность не видна достаточно быстро.
- **Доказательства:** обвал воронки между шагом 3 и 4; 6 из 8 в юзабилити-тесте назвали процесс долгим; 14 тикетов «слишком много вопросов при регистрации».

## 3. Цели и не-цели

**Цели:**
- Поднять завершаемость онбординга до ≥ 75%.
- Довести пользователя до «ага-момента» за ≤ 2 экрана.
- Не потерять качество профиля (заполняемость отложенных полей позже).

**Не-цели:**
- Не переделываем визуал бренда — только структуру и число шагов.
- Не трогаем KYC/платёжные поля — их сокращать нельзя (отдельная история).
- Не делаем персонализацию онбординга по сегментам — это v2.

## 4. Пользователи и сценарии

- Как **новый пользователь**, я хочу быстро попасть внутрь продукта, чтобы понять ценность, не заполняя длинную форму.
- Как **новый пользователь**, я хочу, чтобы недостающие данные спросили позже и в контексте, чтобы не отвлекаться на входе.
- Как **вернувшийся, не достроивший профиль**, я хочу мягкое напоминание дозаполнить, чтобы не потерять доступ к функциям.

## 5. Экраны и состояния  → Builder

- **Экран 1 — Аккаунт (email + пароль/соц-вход):** default · loading · error (занятый email, слабый пароль) · success
- **Экран 2 — Одна ключевая настройка (цель использования):** default · empty (ничего не выбрано) · success
- **Отложенный сбор данных (инлайн, позже):** default · dismissed · error
- **Готово / вход в продукт:** success · empty-состояние продукта для новичка

## 6. Требования

**P0:**
- [ ] Онбординг = ровно 2 обязательных экрана до входа в продукт. Given новый юзер, When проходит вход, Then после 2 экранов он внутри.
- [ ] Отложенные поля собираются позже, в контексте. Given профиль неполный, When юзер доходит до функции, требующей поля, Then поле запрашивается инлайн.
- [ ] Все состояния ошибок дают понятный текст (без «Error 400»).

**P1:**
- [ ] Прогресс-индикатор «шаг 1 из 2».
- [ ] Соц-вход одной кнопкой на первом экране.

**P2:**
- [ ] Персонализация второго экрана по источнику трафика.

## 7. Спорные решения на проверку  → Respondent

- **Соц-вход первым vs email первым** — что даёт выше завершаемость и не роняет качество аудитории.
- **Спрашивать «цель использования» на входе vs отложить её тоже** — не лишний ли это второй экран.

## 8. Ограничения и зависимости

- Отложенный сбор требует поддержки на бэке (флаг «профиль неполный»).
- Аналитика воронки должна уметь мерить новую 2-шаговую воронку до запуска A/B.
