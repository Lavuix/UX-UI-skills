# Research — лёгкая проверка макета на синтетических пользователях

Отдельный от оркестра режим (пункт 5 в приветствии, `/research`): берёт готовый
макет — картинку или ссылку на Figma — и прогоняет его через синтетическую панель
респондентов, без полной сборки фичи. Нужен, когда макет уже есть (свой или чужой)
и вопрос один: «где на нём споткнутся люди», а не «давай соберём экраны».

## Структура

```
research/
├── README.md              ← этот файл
├── base-hypotheses.md     ← библиотека типовых рисков (чек-лист для прогона)
├── personas/               ← библиотека персон (переиспользуемая, как best-practices)
│   ├── INDEX.md             ← индекс: какие персоны уже есть
│   ├── _TEMPLATE.md         ← шаблон новой персоны
│   └── *.md                  ← сами персоны
└── reports/                 ← отчёты по прогонам
    ├── _TEMPLATE.md         ← шаблон отчёта
    └── <ГГГГ-ММ-ДД>-<имя>.md
```

## Как это соотносится с остальным китом

- Персоны отсюда — это те же профили, которыми `respondent` пользуется и внутри
  полного оркестра (`/feature`, шаги 6 и 9c) — библиотека общая, не дублируется.
- `base-hypotheses.md` — типовые риски (находимость, однозначность действия,
  предотвращение ошибок и т.п.), которые можно прогнать без формулирования
  гипотезы с нуля под каждый макет; можно и совмещать со своими.
- Гипотезы, которые всплывают по ходу прогона, заводятся как обычно —
  `../templates/hypothesis.md` → `../hypotheses/`.
- Повторяемая находка из отчёта → как обычно, паттерн в `../best-practices/`.

## Персоны и гипотезы дизайнер выбирает сам

Режим не решает за дизайнера: перед прогоном он показывает список персон и список
базовых гипотез и ждёт ответа — какие брать, свои или базовые. Это осознанный
выбор объёма прогона, а не автоматика, которая молча решила сама.

Логика самого режима — в `.claude/skills/research/SKILL.md`, разбор методов —
в `../playbook/4-testing.md`.
