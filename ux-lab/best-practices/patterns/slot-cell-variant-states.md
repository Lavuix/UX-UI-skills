# Паттерн: слот-компонент с состояниями — один слот на группу, не на вариант

| Поле | Значение |
|------|----------|
| Категория | Компоненты / Figma-платформа |
| Уверенность | ⚪ допущение |
| Источник | Сборка компонента «Таблица» (Table Cell), сессия 2026-08-13 |
| Обновлено | 2026-08-13 |

## Практика

- **Делай:** когда у компонента со слотом (`component.createSlot()`) нужны
  дополнительные варианты состояния (Enabled/Hovered/Pressed и т.п.) поверх уже
  существующего размера — создавай слот **один раз** на группу вариантов, которые
  должны делить контент (например, все State одного Size), а остальные варианты
  этой группы просто **переключи их slot-фрейм на тот же ключ**:
  `slot.componentPropertyReferences = { slotContentId: existingKey }`.
  После этого `componentSet.deleteComponentProperty(oldKey)` подчищает лишние
  автосозданные ключи у клонов.
- **Избегай:**
  1. Клонировать компонент со слотом (`variant.clone()`) и потом звать
     `figma.combineAsVariants([...])` на всём наборе клонов — при пересборке сета
     слот-фрейм иногда молча теряет тип `SLOT` (превращается в обычный `FRAME`,
     `componentPropertyReferences` очищается), а весь **override-контент во всех
     существующих инстансах этого компонента пропадает** без ошибки в консоли.
     Это не баг скрипта — воспроизводится и вручную в Figma при похожих операциях.
  2. Звать `component.createSlot()` отдельно на каждом варианте состояния —
     каждый вызов создаёт **свой уникальный** property-ключ. Внешне в панели
     свойств это выглядит как один и тот же «Content», но при переключении State
     на инстансе (Enabled→Hovered) слот **физически меняется**, и вставленный
     дизайнером контент откатывается на пустой дефолт — выглядит как баг
     компонента, хотя структура вроде бы правильная.

## Почему

При добавлении Hover/Pressed к уже собранному и заполненному инстансами
компоненту `Table Cell` (S/M) стандартный путь — вынести существующие компоненты,
клонировать под новые состояния, `combineAsVariants` — привёл к тому, что слот
на ВСЕХ вариантах (включая нетронутые оригинальные) превратился в обычный frame,
и все 40+ заполненных ячеек в макете разом опустели. Пришлось пересоздавать
слоты (`createSlot()` на каждом варианте) и заново наполнять все ячейки контентом.
После этого второй раз наступили на грабли: `createSlot()` на 3 состояниях одного
размера создал 3 независимых ключа вместо одного общего — переключение State
на инстансе не сохраняло контент. Договорились и починили руками через
`componentPropertyReferences`. Данных/тестов нет, это дисциплина по итогам
одной сессии — уверенность ⚪.

## Когда применимо

- Любой компонент кита с реальным Figma-слотом (`SLOT`, не `INSTANCE_SWAP`),
  у которого появляются новые variant-оси (State и т.п.) поверх уже
  существующего слота с контентом в инстансах.
- Не проверялось на INSTANCE_SWAP-свойствах и на слотах без предварительно
  заполненных инстансов — там риска потери контента может не быть.

## Пример

Figma `M03BFuFuarl4z15GXCFnxh` (Life-20_Kit_Light), страница «Table», компонент
`Table Cell` — Size=S/M × State=Enabled/Hovered/Pressed, node `2182:7031`.
