# 5. Как рисовать (собирать макеты)

Рисование здесь — не «с чистого листа по вдохновению», а сборка из системы под
конкретную гипотезу.

## Принцип: компонент, а не пиксель

- Собираем из компонентов библиотеки и токенов `foundation/tokens.md`.
- Значение «мимо токена» — это баг консистентности, а не творчество.
- В оркестре в Figma пишет только **Builder** — он и собирает экраны из
  опубликованной библиотеки.

## Дисциплина всех состояний

Каждый экран/компонент рисуем во **всех** состояниях, иначе в макете дырка:

`default · loading · empty · error · disabled · success`

Для таблиц добавь: пустая таблица, одна строка, много строк (переполнение),
длинный текст в ячейке, состояние загрузки страницы, ошибка загрузки.

## Порядок сборки

1. Возьми гипотезу и спеку (§5 «Экраны и состояния»). Если есть выбор между
   несколькими концепциями/формулировками — можно прогнать их через
   **claude-persona** (`4-testing.md`) синтетической панелью до того, как
   рисовать все варианты — дешёвый доп. сигнал, не обязательный шаг.
2. Загляни в `best-practices/INDEX.md` — есть ли готовый проверенный паттерн.
3. Собери каркас по сетке и ритму из `foundation` (паддинги, высоты).
4. Наполни компонентами из библиотеки, для каждого — все состояния.
5. Прогони по `2-validation.md` (четыре линзы + чеклист).

## Аннотируй варианты и корнер-кейсы

Если на странице несколько вариантов одного компонента/экрана (размеры,
edge-кейсы, примеры использования) — у каждого рядом добавь аннотацию, а не
только имя слоя:

- Отдельный блок **рядом** с макетом (не оборачивай макет в контейнер/группу —
  аннотация и макет остаются независимыми соседними фреймами).
- Светло-жёлтый фон, auto-layout, паддинг ~12, скругление — читается как стикер,
  не как часть интерфейса.
- Заголовок жирным (название варианта) + короткое пояснение: для чего этот
  вариант и когда его применять («зачем», не «что» — имя слоя уже говорит что).
- Отступ между аннотацией и макетом, и между соседними парами — не впритык
  (иначе зрительно сливается или наезжает при росте одного из макетов).

Зачем: страница с 5+ вариантами без пояснений нечитаема для того, кто не
участвовал в сборке — приходится открывать каждый фрейм и гадать, чем он
отличается от соседнего и в каком сценарии его брать.

## Greenfield и дизайн-система

- `/concept` в оркестре — визуальные направления для проекта с нуля (когда стиля
  ещё нет).
- `/foundation` — собрать дизайн-систему из референса. После этого стиль берём из
  неё, а не изобретаем.

## Правила поверх сборки

Композицию, иерархию и типографику держим по `rules/04-visual-hierarchy.md` и
`rules/02-gestalt.md`; взаимодействие и состояния — по
`rules/03-nielsen-heuristics.md`.
