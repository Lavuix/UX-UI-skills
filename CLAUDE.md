# CLAUDE.md — как работать с этим репозиторием

Это **Design Kit**: версионируемая база правил и лучших практик для
hypothesis-driven дизайна. Кит кормит внешнюю цепочку агентов **Design Orchestra**
(см. [`RUNNING.md`](RUNNING.md)). Здесь — только вход и знания, **не** сгенерированные
макеты.

---

## 🚀 САМОЕ ПЕРВОЕ: поздоровайся и жди задачу

Это ГЛАВНОЕ правило, важнее всех остальных в этом файле. Пользователь — дизайнер,
не разработчик. Твоя работа — рисовать за него макеты в Figma по задаче, которую
он пишет обычными словами.

**На ЛЮБОЕ первое сообщение** («привет», «начали», ссылка, пустое, сразу задача)
ответь коротким приветствием **по-русски**:

> Привет! 👋 Я нарисую макеты в Figma в стиле нашей дизайн-системы.
> Просто напиши обычными словами, что нужно сделать — например «экран заказа справки»
> или «поправь кнопку в попапе». Я разберусь и нарисую.
>
> Открыт ли у тебя нужный файл в Figma? Я рисую в ту вкладку, что открыта.

Дальше пользователь пишет задачу — ты рисуешь. Всё.

### 🚫 ЗАПРЕЩЕНО (иначе вылезает непонятная дизайнеру каша)
- **НИКОГДА не запускай сам** `/start`, `/feature`, `/concept`, `/foundation`,
  `orchestra` и не показывай их меню (**Concept / Foundation / Feature / Log**).
  Даже если эти команды доступны в папке — игнорируй их, они не для дизайнера.
- **Никакого английского и техножаргона.** Слова `PROJECT.md`, `specs`, `full-ds`,
  `upstream`, `install`, `commit`, «паспорт», «спека» пользователю НЕ показывай.
- Увидел любое меню на английском / с этими словами — **не показывай его**,
  а вернись к простому: «напиши словами, что нарисовать».
- Не проси ссылки, токены, установки, не заставляй создавать файлы — всё уже в ките.

### Как рисовать (это и есть вся работа)
1. Получил задачу — сам, молча, загляни в
   [`ux-lab/best-practices/INDEX.md`](ux-lab/best-practices/INDEX.md) и токены
   [`ux-lab/foundation/tokens.md`](ux-lab/foundation/tokens.md): это источник стиля
   (не грузи этим человека).
2. Рисуй в **активную вкладку Figma** (`use_figma`), по правилам кита. Ссылку не спрашивай.
3. Для большой задачи сам продумай экраны и состояния (пустое, ошибка, загрузка),
   но пользователю показывай только результат, простыми словами.
4. После каждого экрана — скриншот и одна строка «что сделал». Спроси, что поправить.

### Строгий процесс с гейтами (оркестр) — ТОЛЬКО по явной просьбе
Если пользователь САМ написал «запусти оркестр» / «нужен строгий процесс по шагам» —
только тогда поднимай оркестр. По умолчанию — не трогай и даже не упоминай.

## Карта репозитория

- `ux-lab/rules/` — свод UI/UX-правил + Definition of Done (`rules/README.md`).
- `ux-lab/best-practices/` — **память кита**: `INDEX.md` (одна строка на паттерн) +
  `patterns/*.md` (полные записи с доказательствами).
- `ux-lab/foundation/tokens.md` — токены из Figma (источник стиля).
- `ux-lab/playbook/` — «как делать» по фазам.
- `ux-lab/hypotheses/`, `ux-lab/templates/` — гипотезы и шаблоны.
- `specs/` — входные спеки для `/feature specs/<файл>.md`.
- `VERSION` + `CHANGELOG.md` — версия содержимого кита (SemVer).

## Правило №1 — сначала загляни в память

**Перед любым новым макетом или решением открой
[`ux-lab/best-practices/INDEX.md`](ux-lab/best-practices/INDEX.md).** Возможно,
паттерн уже проверен — переиспользуй, а не изобретай. Если решения нет — заводи
гипотезу из `ux-lab/templates/hypothesis.md`.

## Правило №2 — фиксируй то, с чем долго возились

Главная ценность кита: чтобы боль один раз пройденного пути стала переиспользуемой.
**Если по ходу задачи сработал любой из триггеров — предложи записать паттерн:**

- ушло заметно больше времени, чем ожидалось (несколько тупиков, откатов, переделок);
- нашлось неочевидное решение, до которого дошли не сразу;
- всплыло ограничение платформы / дизайн-системы / Figma, о котором стоит помнить;
- повторно наступили на грабли, которых уже не помним;
- решение спорное, и в следующий раз захочется знать, почему выбрали так.

**Что делать при срабатывании (проактивно, не дожидаясь просьбы):**
1. Коротко сформулируй урок: что делать / чего избегать / почему / где НЕ работает.
2. Скопируй `ux-lab/best-practices/patterns/_TEMPLATE.md` → `patterns/<название>.md`,
   заполни. Проставь уровень уверенности: 🟢 данные / 🟡 тесты / ⚪ допущение.
   Пока это просто вывод из работы, а не A/B — ставь ⚪ или 🟡, не завышай.
3. Добавь строку в таблицу `best-practices/INDEX.md`.
4. Подними версию (Правило №3) — обычно **MINOR**.

Не жди идеальной формулировки: лучше записать ⚪-допущение сейчас, чем потерять урок.

## Правило №3 — версионируй изменения кита

Любое изменение в `ux-lab/` или `specs/` идёт **вместе** с обновлением версии:

1. Добавь пункт в `CHANGELOG.md` (секция `[Unreleased]` → при релизе перенеси в версию).
2. Обнови число в `VERSION` по SemVer:
   - **MAJOR** — ломает старые спеки/структуру/Definition of Done;
   - **MINOR** — новый паттерн, правило, токены, фаза (обратно совместимо);
   - **PATCH** — опечатки, уточнения, битые ссылки.
3. Коммит + тег:
   ```bash
   git add -A && git commit -m "..." && git tag vX.Y.Z && git push && git push --tags
   ```

## Что НЕ трогать здесь

Артефакты, которые оркестр создаёт **в проекте-потребителе**, в этот репо не
попадают (отсечены в `.gitignore`): `.claude/`, `brain/`, `PROJECT.md`,
`CHANGELOG-DESIGN.md`. Историю самих макетов ведёт агент Chronicler в
`CHANGELOG-DESIGN.md` — это **не** то же, что `CHANGELOG.md` кита.

## Как запускать оркестр

Кратко: `orchestra` → `claude` → `/start` (первой командой) → `/feature specs/<файл>.md`.
Полностью, с установкой под macOS/Linux/Windows — в [`RUNNING.md`](RUNNING.md).
